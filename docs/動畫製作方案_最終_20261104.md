## 1. 三種方案的實測對比

三種都用同一張立繪、同一套動作定義、同一支渲染器跑 `sa`（96 幀），只換「怎麼拆、怎麼綁」。

| 方案 | 做法 | 四邊形/幀 | manifest | 邊長畸變（最大/平均） | 本體盲評 | 結論 |
|---|---|---|---|---|---|---|
| **A 部件骨骼** | 9 個語意部件，各自低密度網格（剛體 1×1、軀幹 3×4、四肢 2×3） | **46** | **1.15 MB** | 1.31 / 1.0019 | **8–9** | ✅ **採用** |
| B 全圖網格 | 整張圖一個 8×10 網格，權重按到骨距離自動算 | 80 | 1.99 MB | **1.72** / 0.9973 | 8 | ❌ 邊長畸變最嚴重 |
| C 部件剛體 | 同 A 的切法，但每部件 1×1（純仿射，不做網格形變） | **9** | **0.22 MB** | 1.13 / 1.0027 | 7 | ❌ 腰際出現黑色斷裂接縫 |

### 量測方法

- **邊長畸變**：每個網格四邊形變形後邊長 ÷ 原始邊長。>1.35 是肉眼可見的拉伸。
- **面積畸變**：四邊形面積比開根號。>1.5 會明顯「橡皮感」。
- 量測已排除 `ringR`（頭後環）的 1.5 —— 那是 `motion.mjs` 刻意寫的「開火炸開」縮放，不是網格瑕疵。

### 為什麼不是 B

B 的邊長畸變 **1.72** 是三案最差。原因很具體：整張圖一個網格時，
「肩砲」和「頭」共用同一批頂點，砲後坐的位移會把旁邊的頭一起拖走。
A 把砲切成獨立剛體、100% 綁砲骨，就完全沒有這個問題（1.31 只剩披風的刻意擺動）。

### 為什麼不是 C

C 的數字最漂亮（9 個四邊形、0.22 MB），但**視覺上會裂**。
Vision 模型對 C 的評語是「頸部與右腿膝蓋處有明顯黑線斷裂，嚴重錯位，整體明顯像拼貼紙片」。
原因是：軀幹與腿各自做仿射變換，但兩者是硬切開的，變形後邊界不再重合 → 露出背景。
A 用兩件事解決：

1. **bleed（相鄰部件重疊 3–5px）**：後畫的蓋住先畫的，重疊區取同一張原圖像素，靜止時看不出來。
2. **blend 權重**：腿的上緣與披風的上緣跟軀幹做線性權重過渡，接縫處是連續變形的。

C 兩者都沒有，所以必裂。**A 只比 C 多 37 個四邊形，卻換來完全不同的品質**，這個交換非常划算。

## 2. 墜星動作規格

`fps 24`，座標以立繪像素為單位，`facing: 'left'`（立繪朝左、砲口朝左上）。

| 序列 | 幀數 | 時長 | 命中幀 | 循環 | 對照官方基準 |
|---|---|---|---|---|---|
| `standby` | 48 | 2.00s | — | ✅ | — |
| `sa` | 96 | **4.00s** | 58（2.42s，60%） | — | 特殊 sa 中位 **4.04s** ✔ |
| `ultimate` | 120 | 5.00s | 72（3.00s） | — | 第五技能（絕招，全屏層） |
| `hited` | 8 | **0.33s** | — | — | 受擊中位 **0.33s** ✔ |

### sa 分鏡（實作值）

```
幀  0–20   蓄能：砲口雙環從 1.7 倍收緊到 0.95，浮游翼亮起，軀幹微微前傾
幀 20–38   聚氣：環收到 0.5，光暈 1.35 倍，肩砲往後拉 22px
幀 38–46   後坐：軀幹後仰 6.5°，砲身往後 34px（snap 緩動，瞬間到位）
幀 46      開火：白光 1.6 倍炸開、光束往左射 900px、粒子噴出
幀 46–58   彈道：光束擴散、閃光衰減、砲身劇烈震盪（±5°）
幀 58      命中：action_hit 標記
幀 58–82   餘波：餘震遞減、光暈收斂
幀 82–95   收招：全部歸零
```

### 為什麼這樣設計

- **命中在 60%**：4.00s × 0.60 = 2.40s = 第 58 幀。官方 sa 中位 4.04s，命中點落在 2.4s 附近，跟「先蓄力、再放」的節奏一致。
- **首段用 `inOut` 不用 `charge`**：`charge` 是 t³，起步速度接近 0，實測讓第 1–3 幀**完全靜止**（相鄰影格變動率 0%），開頭看起來像卡住。改 `inOut` 後最低變動率升到 0.35%，全序列零靜止幀。
- **待機幅度刻意拉大**：初版質心位移只有 5px（927px 畫布），Vision 模型判定「幾乎靜止」。拉到 x 8px / y 14px 後才讀得出「有在呼吸」。首尾必須同值（loop 不跳）。

## 3. 管線設計

```
立繪 PNG
   ↓ parts.mjs    9 個語意多邊形 → 每個不透明像素指派給唯一部件
   ↓              多邊形沒蓋到的殘餘像素用 BFS 併進最近部件（零遺漏）
   ↓ rigCore.mjs  每部件裁貼圖（含 bleed 重疊）→ 低密度網格 → 骨骼權重
   ↓ motion.mjs   骨骼軌道（關鍵影格 + 緩動）+ 光效軌道
   ↓ build_zhuixing_skeletal.mjs
public/elf-anim/wuxu_zhuixing/{atlas.png, manifest.json}
   ↓ customPetClip.ts → SwfClipData
SwfPlayer（一行都不用改）
```

### 檔案

| 路徑 | 作用 |
|---|---|
| `scripts/build_zhuixing_skeletal.mjs` | 烘焙器（可重跑、可換精靈） |
| `scripts/lib/skeletalRig/parts.mjs` | 部件多邊形 + 骨骼 + 網格密度 |
| `scripts/lib/skeletalRig/rigCore.mjs` | 切分／權重／蒙皮／光柵化／時間軸 |
| `scripts/lib/skeletalRig/motion.mjs` | 四段動作的骨骼軌道與光效軌道 |
| `scripts/lib/skeletalRig/fx.mjs` | 程序化光效（ring / glow / beam / spark） |
| `docs/custom-anim/wuxu_zhuixing.skel.json` | 這隻精靈的設定（來源圖、縮放、留白） |
| `public/elf-anim/wuxu_zhuixing/` | 產出的圖集與 manifest |

```bash
node scripts/build_zhuixing_skeletal.mjs --preview   # 先看關鍵影格 + GIF
node scripts/build_zhuixing_skeletal.mjs             # 烘焙正式素材
npm run test:custom-anim                             # 格式契約（32 項）
npm run test:custom-anim:browser                     # 真實播放器截圖
```

### 關鍵設計決策（每一條都是踩過坑換來的）

1. **剛體一律 1×1 網格。** 旋轉／位移／縮放是仿射變換，單一四邊形在數學上就是精確的。給砲鋪 4×5 網格純屬浪費。上次 48×62 網格 = 835 萬個數字、manifest 41.9 MB 就是死在「對不需要形變的部件也鋪密網格」。
2. **部件之間要有 bleed。** 硬切的部件各自變形後必定裂開（實測頸部、腰際出現黑線）。讓相鄰部件重疊 3–5px、後畫的蓋住先畫的，重疊區取同一張原圖像素，靜止時完全看不出來。
3. **blend 權重的方向不能寫反。** 頭的 `ownAt: 'top'`（頭骨管頭頂、底部漸變到軀幹）。寫成 `bottom` 的話頭頂會跟著軀幹走、脖子跟著頭走，一轉頭脖子就裂。
4. **auto 權重要限定骨骼池。** 軀幹只跟 `root/torso/head/legL/legR` 混合。若讓砲骨、翼骨也參與，後坐時軀幹會被砲拉著走，看起來像整個人被吸向砲。
5. **光效用低解析度烘焙。** ring/glow/beam/spark 都是柔和漸層，靠紋理雙線性放大還原，肉眼分不出來，但圖集面積直接砍 16 倍（`FX_K = 0.25`）。
6. **manifest 數字精度：位置 3 位、UV 5 位小數。** PPU=100 時 0.001 世界單位 = 0.1 畫布像素，肉眼不可見；少這兩位讓 manifest 從 3.7 MB 掉到 1.45 MB。
7. **draw call 的真相**：播放器是「每個 subMesh 一個 PixiJS Mesh」，不是每個四邊形。所以 46 個四邊形其實只有 **2 個 subMesh**（本體 + 光效）。46 這個數字保守地當作頂點預算在用。

## 5. 如何套用到另外 3 隻

管線本身是通用的，每隻精靈只需要換三樣東西：

### 步驟

1. **複製 `scripts/lib/skeletalRig/`** 成該精靈的目錄（或直接在 `parts.mjs` / `motion.mjs` 加一組匯出）。
2. **寫該精靈的 `parts.mjs`**：定義部件多邊形 + 骨骼 + 網格密度。
3. **寫該精靈的 `motion.mjs`**：四段動作的骨骼軌道與光效軌道。
4. **寫 spec**（`docs/custom-anim/<id>.skel.json`）：來源圖、縮放、留白。
5. **烘焙 → 測試 → 更新登記表**。

### 各精靈的預期工作量

| 精靈 | 技能組成 | 需要的序列 | 難度 | 備註 |
|---|---|---|---|---|
| **5022 無序.六刃** | 物理×5 | `standby` `attack` `hited` | 中 | 六把刃環身，適合「環繞收束 → 前衝揮擊」。朝右。 |
| **5023 無序·蝕言** | 物理×3、特殊×2 | `standby` `attack` `sa` `extra` `hited` | 中高 | 5 段最多。書頁翻動用網格變形做得到（薄片最適合蒙皮）。 |
| **5017 人皇·帝辛** | 物理×4、屬性×1 | `standby` `attack` `cp` `hited` | 中 | 金光聚於劍身 → 前衝斬擊。披風與袍襬是重點。 |

### 切部件時的實務建議

- **先跑佔用率圖**（見 `docs/動畫方案製作筆記` 的量測腳本做法），用 40px 網格讀出輪廓，**不要憑感覺畫多邊形**。我一開始用視覺模型讀座標網格，它給的數字偏差 300px 以上，完全不能用。
- **切分順序＝優先序**：會與別人重疊的（例如頭後環壓在頭髮上）要排在前面先吃像素。
- **剛體部件**（武器、浮游機、飾品）→ `1×1` + `rigid`。
- **有內部形變的**（軀幹、披風）→ `2×3` ~ `3×4` + `blend` 或 `auto`。
- **bleed 給 3–5px**，接縫才藏得住。
- **確認朝向**：`facing` 必須跟 `BODY_SOURCE_FACING` 一致（帝辛/蝕言/墜星朝左、六刃朝右），否則動畫與靜態圖會突然轉身。

### 建議的下一步

1. **六刃**先做（最簡單，純物理、3 段）。
2. **帝辛**次之（劍與披風，`cp` 屬性技能可以只用光效 + 輕微抬手）。
3. **蝕言**最後（5 段最多，且 `extra` 需要新的分鏡設計）。

## 6. 已知限制與未解問題

1. **單張立繪做不出真正的肢體動作。** 現在能做的上限是「軀幹後仰、肩砲後坐、浮游機張合、披風擺動、頭部轉向」。要揮劍、抬腿、轉身，需要**分層立繪**（美術提供拆好圖層的 PSD）—— 這是管線能力的邊界，不是參數沒調好。
2. **背面看不到的部件不存在。** 立繪只有正面，角色轉超過約 25° 就會露出「沒有背面」的破綻。目前所有動作都控制在這個角度內。
3. **光效是程序化的**，沒有手繪特效的細節（雲霧、碎片、能量拉絲）。好處是可調參數、可重現、檔案小；代價是比不上官方素材的手繪爆炸。
4. **圖集 7.29 MB 偏大。** 主要來自 272 幀各自一格光效。若要再壓，可以：
   - 把光效軌道改成「共用圖集 + 逐幀 UV 位移」（目前每幀獨立格）
   - 或把 `ultimate` 的 120 幀砍到 90 幀（5.0s → 3.75s，仍在合理範圍）
5. **`ultimate` 走全屏層**（`fullscreen: {ultimate: 'ultimate'}`），這是既有機制，本次沒有改動它的行為。

## 附錄：量測腳本的做法（給後續精靈參考）

「部件切分」這一步最容易出錯，也最難用肉眼驗證。有效的做法是：

1. **印出 40px 解析度的「色彩類別圖」**（黑/深灰/白/青/紅/黃…），對照它一格一格畫多邊形。
2. **把切分結果塗成彩色疊回原圖**，用視覺模型檢查「哪裡切錯」。
3. **把每個部件單獨輸出成白底 PNG**，逐張問「多了什麼、少了什麼」。
4. 重複 2–3 直到乾淨。

我這一輪迭代了 3 次才乾淨（第一次頭部吃到肩膀、第二次軀幹吃到披風、第三次才對）。
**不要相信視覺模型讀座標網格的能力** —— 它給的邊界框誤差達 300px；但讓它判斷「這張圖切得對不對」非常準。
