## 2. 補齊 342 份的做法（每批 1 隻精靈，最多 6～8 份定義）

### 2.1 每批流程

1. 從 `block-migration-queue-342.md` 取**同一隻精靈**的項目。建議先做未解分支少的：5005 → 5004 → 5003 → 5002 → 5020 → 5030 → 5026 → 300 …，最後才碰 5034／5035／5029／5019 這類大魂印。
2. 讀原文：`elf_source_files/elf_files/<ID>_*.txt`（以 TXT 為準），再對照 `docs/audits/elves/<ID>.md` 的逐句表。
3. 每一句判斷是哪一種：
   - **A 已有原子可表達**：用 `sequenceContract.ts` 列出的動作／條件組合，寫成 Kit。
   - **B 需要新的通用原子或條件**：**不要在這批硬做**，記到第 4 節「通用缺口清單」，該定義維持 needs-definition。
   - **C 原文有歧義**：記到「待使用者確認」，維持 needs-definition。
4. 只有整份定義**每一句都是 A**，才能把它轉成可編輯 Kit。部分轉換一律不准（這是過去「替代實裝」的根源）。
5. 測試：每份新 Kit 至少要有以下真實戰鬥情境，可參考 `tests/composedBlockEffects.integration.test.ts`、`reviewedSequenceKits.integration.test.ts`：
   - P1 與 P2 各一次。
   - 條件成立／不成立。
   - 成功／失敗分支（原文有「成功則／未觸發則」時）。
   - 附加效果失效時不執行。
   - 有回合數的檢查到期；有下場保留的檢查換人；有傷害的檢查傷害類型與數值。
6. 跑 `npm run lint`、本批新測試、`npm run audit:block-migration`。追蹤表中該項才可改為「candidate-verified」。
7. 在 `docs/共同機制與實裝修復計畫_20261004.md` 末尾追加一段：原文 → 執行路徑 → 測試初始狀態 → 預期／實際 → 未確認項目。
8. `git commit`（不要 push）。

## 5. 使用者已確認的規則（衝突時以這裡為準）

- 攻擊傷害是技能傷害的子集；固定、百分比、真實傷害與體力調整各自分開。
- 吸取固定值＝固定傷害；吸取比例＝百分比傷害；汲取＝真實傷害。吸血依結算值，不受對手剩餘體力限制。
- 「傷害提升100%並恢復等量體力」的等量＝本次攻擊傷害。
- 「下次」可在當次後續節點觸發，但不能追溯已結算的節點。
- 連擊＝一次公式、一次動畫；額外行動＝獨立節點。六刃例外：多個邏輯節點、只播一次動畫。
- 異常沒寫回合數時預設 3 回合；同名異常合併回合數。機率用 PRD。
- 蟲后六維加成＝含體力的六維總和 × n × 10%，每維加同一個數；PP 吸取＝對手每招 -2、自己每招 +2。
- 蟲群庇護的禁切換對象是對手。
- 雷伊異能值是無效果佔位，不要動；靈光之怒公式不動；5011 金光綠葉「星海之浸」照原文。
