# 兩個特殊模式：呼叫鏈稽核與修復順序

2026-10-02。對照 `P0-P2_修復工單_20261001.md` 後重新讀取目前程式，不把另一位AI的分析當驗證。以下為靜態證據；尚未完整遊玩重現、尚未修復特殊模式戰鬥與經濟。此批只擴充搜尋，不更動模式規則。

## 星際探索

| 優先 | 問題 | 程式證據 | 修復／驗收要求 |
| --- | --- | --- | --- |
| P0 | 戰後結果未回探索 | Run的`startRealBattle`傳`onBattleEnd`；App只轉配裝/format/interstellarOptions，BattleScreen沒有接該回呼 | 不能只補一個prop：切到battle會卸載Hub/Run，舊closure不能更新已卸載的探索。先把run快照與一次性結算移到持久層；勝/敗/退出、重開存檔均驗 |
| P1 | 藏品、難度與裝備的面板可能不生效／重複 | Run改`baseStats`後仍spread舊`calculatedStats`；敵隊倍率也保留舊面板。下游裝備與開局reset信任calculatedStats | 明確種族值/面板/戰鬥快照三層；只重算一次；加乘順序及不滿血入場不能靠reset自動補滿。測同精靈前後HP/攻/速及重複戰鬥 |
| P1 | 起始鑽石忽略設定 | Hub計算`startingDiamonds`並傳Run；Run初始`diamonds`用`getSavedRunValue('diamonds',3)` | 新局用傳入值；有效舊局恢復存檔；免費/購買難度配置逐項測 |
| P1 | 移動觸發舊節點 | `handleMoveToNode`setLayers後timeout50呼叫該render的`handleEngage`，其currentNode仍是舊closure | 直接以已確認target節點決定事件；不能依timeout猜React更新時點；戰鬥→商店、銀行→回復連續移動測 |
| P1 | 沒有在handler檢查連線可達性 | 移動handler只驗fuel，沒檢查target是否位於current.connections | 即使UI限制也需入口驗證；非法/跨層/不存在target不得扣fuel |
| P1 | 招募券在打開候選時扣除 | `handleUseVoucher`先減券，確認招募是後續另一函式 | 是「看候選就消耗」還是「確認才消耗」需先確認設計；取消、重開、隊伍滿/鑽石不足測，不能擅改經濟 |
| 待定 | 海盜銀行扣留本金能否在勝利追回 | 海盜伏擊分支清bankBalance，提示本金扣留後進combat；戰後鏈未接 | 先修結算鏈，再依設計釐清追回額、失敗損失。不可將此直接當正常銀行漏退款 |

重要反證：目前基斯克銀行確實加回本息後清balance；商人銀行失敗退款一半、成功加回本息；海盜無伏擊也加回本息。因此舊工單「提領全部都漏加回」不符合現有程式，不照該推測修改。

## 命運之輪

| 優先 | 問題 | 程式證據 | 修復／驗收要求 |
| --- | --- | --- | --- |
| P0 | 隨機附加攔截效果的全域runner未接 | `handleDestinyInterceptor`僅在battleEventRegistry匯入及`GlobalBattleEventRegistry`匯出；全src沒有後者呼叫者 | 先確認單隻原生魂印的攔截避免重複，再接模式專屬事件、死亡/登場去重。不能認為五個效果已透過此路實裝 |
| P0 | 舊runner從錯誤存放區取rank/effect/maxHp | 用getPlayerState讀取；卡池寫的是Elf.destinyRank/interceptorEffect，HP也屬Elf | 接線前從實際self/target及持久轉移資料讀取；所有有限數值防NaN與同ID多實例測 |
| P1 | 舊runner即使接線也不符合五種定義 | 封技用未登記異常；PP寫側狀態函式而非更新技能/PP上限；索魂用衰弱模擬先制-2；英靈只排pending而非全隊；悲歌從側狀態取HP | 為五種各建準確primitive與事件/作用域測試；不是改log掩蓋效果。悲歌需護罩不是護盾、所有異常免疫不是只免控 |
| P1 | 模式隔離需確認 | imperialShieldRegistry登場封技放在empShieldInited初次登場區段，沒有destiny模式條件；同名handler在多Registry匯出，最後寫入覆蓋 | 查目前實際勝出handler與普通/命運雙情境；通用魂印與模式攔截不得重複或外溢。不能把某個未啟用舊handler當真實路徑 |
| P1 | 一般參考評級與模式評級不同 | getElfDestinyRank優先舊destinyRank，未列名者種族值≥730或技能≥6升S；首頁elfDisplayRank以命運專屬文本先判C且不用技能數升S | 先確認要統一模式卡池規則，或明確標示不同規則；原規則變更需保底分布回歸 |
| P1 | 短池不能保證12張與指定階級 | perform12Pull不足某級從全池補；按名字去重，總池太小就少12；classic補充只有1個 | 定義短池替補政策；0/1/5/12張、缺S/缺A/缺C測；不假裝1S3A2C永遠滿足 |
| P2 | 排序亂數不是等概率洗牌 | `.sort(()=>Math.random()-0.5)`多處 | 以可注入RNG的Fisher–Yates；固定種子復現與分布檢查 |
| P2 | 圖鑑預覽與實際重建卡池可能不同攔截 | buildDestinyPool每次隨機給缺攔截C卡效果 | 同局預覽/抽卡用相同池快照；不用UI裡反覆隨機重建 |

沒有宣稱所有C級原生效果都沒實裝：本報告確認的是隨機卡池效果的全域路徑未接，其他精靈自己的原生Registry另有部分實作，仍要逐隻查實際登記與TXT。
