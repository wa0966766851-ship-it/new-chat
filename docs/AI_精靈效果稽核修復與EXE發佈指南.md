# AI 精靈效果稽核、修復與 EXE 發佈指南

更新日期：2026-09-28

這份文件提供給後續接手本專案的 AI 或開發者使用。目標不是快速宣稱「已完成」，而是建立一套可以重複驗證的流程，回答以下三個問題：

1. 某一條技能、魂印或特質描述是否真的有執行？
2. 發現描述與程式不一致時，應如何修復且避免重複執行？
3. 專案完成後，應如何製作成可交付給玩家的 Windows EXE？

## 一、檢查工作的基本原則

### 1. 不得相信聊天紀錄中的完成宣告

聊天紀錄只能當作待查線索。判定完成必須同時具有下列證據：

- 描述來源存在，且能指出原始 TXT 或資料檔位置。
- 程式中能找到唯一且明確的執行路徑。
- 執行時掛在正確的戰鬥節點。
- 有測試斷言實際狀態變化，而不只是「沒有崩潰」。
- `lint`、`test`、`build` 全部通過。
- 若涉及畫面，必須實際啟動後操作驗收。

只符合其中一部分時，必須標為「部分實裝」或「未驗證」，不可標為完成。

### 2. 五種狀態必須分開

| 狀態 | 意義 |
| --- | --- |
| 描述存在 | UI 或資料檔中有文字，不代表有程式效果。 |
| 解析成功 | 描述可被轉成積木節點，不代表積木已接到戰鬥流程。 |
| handler 存在 | 有專屬程式，但不代表事件會在正確時點呼叫。 |
| 執行路徑接通 | 戰鬥節點確實會呼叫效果，但仍可能算錯數值或目標。 |
| 語意驗證通過 | 測試證明輸入、節點、狀態轉換與結果符合描述。 |

覆蓋率不得把上述狀態混成一個百分比。

### 3. 隨機對戰不是語意測試

隨機對戰只能證明：

- 沒有立即崩潰。
- 流程沒有明顯死循環。
- 常見操作可以走到戰鬥結束。

它不能證明：

- 傷害類型正確。
- 效果在正確節點觸發。
- 先後手、必中、命中率、技能無效與附加效果失效的順序正確。
- 回合、次數、下場保留與死亡後保留正確。
- 固定、百分比、真實、技能與額外行動傷害的互動正確。

## 三、AI 接手時的標準檢查流程

### 階段 A：建立可信基線

1. 執行 `git status --short`，記錄所有既有修改與未追蹤檔案。
2. 執行 `git branch --show-current` 與 `git remote -v`。
3. 不覆蓋、不還原、不刪除不屬於本次工作的變更。
4. 執行：

```powershell
npm run lint
npm test
npm run build
```

5. 將失敗分成：環境問題、既有問題、本次回歸問題，不可混寫。

### 階段 B：建立描述清單

每隻精靈至少拆成：

- 基礎資料與屬性。
- 魂印／專屬特性。
- 二代特質與專屬特質。
- 五個攜帶技能及技能替換庫。
- 出場、回合開始、選技、出手前、傷害前、命中後、出手後、出手流程結束、回合結束、受擊、致死、死亡、下場、場下與戰鬥結束效果。

每一個句子建立獨立編號，禁止把多個條件與多個效果只算成一條「已完成」。

### 階段 C：追蹤唯一執行路徑

依序檢查：

1. `src/data/defaultElves.ts` 或該精靈的獨立資料檔。
2. `src/blocks/parse.ts` 是否可解析描述。
3. `src/blocks/specs.ts` 是否登記為 blocks 或混合模式。
4. `src/blocks/registry.ts` 是否在對應事件執行。
5. `src/effects/*Registry.ts` 是否有專屬 handler。
6. `src/effects/battleEventRegistry.ts` 是否有技能、魂印與觀察者映射。
7. `src/components/BattleScreen.tsx` 是否真的發出該戰鬥事件。
8. `src/battle/contextBuilders.ts` 提供的操作是否走中央傷害、恢復、異常與計時器流程。

若同一句同時由 kit、handler、blocks 與 fallback 執行，必須先消除重複，再談數值修正。

### 階段 D：判定結果

每條效果使用以下欄位記錄：

| 欄位 | 內容 |
| --- | --- |
| 精靈／技能 | 唯一名稱及 ID |
| 原始描述 | 不改寫原意的完整句子 |
| 觸發節點 | 例如 `ROUND_START`、`BEFORE_DAMAGE`、`ACTION_END` |
| 條件 | 體力、先後手、異常、能力等級等 |
| 目標 | 自身、對手、己方全隊、場下或額外精靈 |
| 動作 | 傷害、恢復、異常、能力變化、PP、計時器等 |
| 執行來源 | blocks、handler、kit 或 fallback，只能有一個主責來源 |
| 測試 | 測試名稱與斷言結果 |
| 狀態 | 已驗證／部分實裝／未實裝／描述不明 |

## 四、修復既有精靈效果的標準流程

### 1. 先固定語意，再改程式

遇到描述可能有多種解釋時，先向設計者確認：

- 「吸取」「汲取」「恢復」「直接增加體力」是否為不同事件。
- 傷害屬於技能、固定、百分比、真實或額外行動傷害。
- X 系技能傷害是否吃克制、護盾、攻擊免疫與傷害限制。
- 「必中」與技能命中率是否分開。
- 「技能無效」「固有效果失效」「附加效果失效」各自阻止哪些內容。
- 效果是本回合、下一回合、若干次，或下場／死亡後保留。
- 多次傷害是多個節點，還是一次動畫內的合併傷害。
- 體力歸零是死亡、免死、凍結於零，或允許負體力。

確認結果要寫入 TXT、測試名稱或程式註解，不能只留在聊天中。

### 2. 選擇正確的實裝層

- 一般且可組合的效果：優先增加積木能力。
- 精靈獨有且涉及複雜狀態機：使用專屬 handler，但需保留可讀的機制資料。
- 跨精靈共用規則：抽到 `src/battle` 或 `src/utils`，不要複製到每隻精靈。
- 傷害、恢復、異常、PP 與計時器：必須走 `BattleEventContext` 的中央操作，避免直接改 `currentHp` 或繞過事件。

### 3. 對齊正確戰鬥節點

常用事件包括：

- `ON_ENTRANCE`：登場。
- `ROUND_START`：回合開始。
- `BEFORE_SKILL`：扣 PP 與技能執行前。
- `BEFORE_ACTION`：本次出手開始前。
- `MODIFY_PRIORITY`：先制與必定先手。
- `BEFORE_DAMAGE`：增傷、減傷、上限與保底。
- `ON_SKILL_HIT`：命中後效果。
- `ON_DAMAGED`：實際受傷後。
- `AFTER_ACTION`：使用技能後。
- `ACTION_END`：出手流程結束，即使因故未能正常出手也可能觸發。
- `EXTRA_ACTION_START/END`：額外行動獨立節點。
- `BATTLE_PHASE_END`、`ROUND_END`：戰鬥階段與整回合結束。
- `FATAL_RESIST`、`DEATH_NODE_1/2`：致死與死亡流程。
- `ON_SWITCH_OUT`、`BATTLE_END`：下場與戰鬥結束。

不要用回合結束事件模擬出手後事件，也不要用動畫播放時間代表戰鬥節點。

### 4. 先寫失敗測試

每個修復至少包含：

- 正常觸發。
- 條件不成立時不觸發。
- 免疫／無效／抵擋時的結果。
- 邊界值，例如 0、1、恰好 1/2、最大層數與最大回合數。
- 下場、重新登場、死亡與重生後是否保留。
- 同一效果不重複執行。

測試應斷言體力、PP、能力等級、計時器、印記、狀態與事件記錄，而不是只斷言函式沒有丟出錯誤。

### 5. 修復完成的最低標準

一隻精靈只有在以下條件全部成立後才能標為完成：

- 每條描述都有狀態與執行來源。
- 沒有未解釋的 fallback。
- 技能與魂印不重複執行。
- 所有關鍵節點都有語意測試。
- 與護盾、護罩、異常、PP、換人、死亡及額外行動的關鍵交互已測。
- 詳情頁顯示內容與 TXT 相同。
- `lint`、`test`、`build` 通過。

## 五、新增並實裝一隻精靈需要什麼

### 1. 設計資料

- 唯一 ID、正式名稱、屬性、等級、身高、體重、性別。
- 六項種族值與總和。
- 魂印名稱、徽記字與完整描述。
- 二代特質、專屬特質、通用特質是否存在；不可把數個專屬特質塞進通用特性摘要欄。
- 至少五個技能：名稱、屬性、類型、威力、PP、命中率、先制、固有效果及附加效果。
- 技能替換庫、第五技能、隱藏轉化技能。
- 下場保留、死亡保留、場下效果、額外精靈、特殊資源與上限。

### 2. 美術資源

- 原始全圖立繪。
- 頭像裁切圖。
- 左右視角顯示規則；對戰 P1/P2 需確認是否水平翻轉。
- 新屬性圖示及透明背景。
- UI 中的 `object-fit`、縮放、遮罩、層級與背景遮擋驗收。
- 圖片只能做確定性的裁切、縮放或壓縮時，應保留原圖，不可擅自生成替代圖。

### 3. 引擎能力盤點

新增前先確認引擎是否已支援：

- 所需的觸發節點。
- 傷害分類與傷害節點。
- 屬性克制與最佳克制選擇。
- 必中、命中率、技能無效、固有效果失效與附加效果失效。
- 額外行動、連擊、轉化技能與隱藏技能。
- 負體力、免死、重生、消逝與額外精靈。
- 回合、次數、印記與下場後保留計時器。
- 全隊、場下與敵我觀察者事件。

缺少共用能力時，先補核心引擎與測試，再寫精靈 handler，避免每隻精靈各做一套不相容邏輯。

### 4. 建議檔案配置

- `elf_source_files/elf_files/<ID>_<名稱>.txt`：權威描述。
- `src/data/<elfName>.ts`：精靈資料、技能與隱藏轉化技能。
- `src/effects/<elfName>Registry.ts`：專屬狀態機與技能 handler。
- `src/effects/battleEventRegistry.ts`：映射與需要的場上／場下觀察者。
- `src/data/defaultElves.ts`、`src/data/elfRegistry.ts`：預設登記與舊快取升級。
- `src/blocks/specs.ts`：積木執行模式。
- `tests/<elfName>.semantic.test.ts`：語意測試。
- `public/elf-art/`、`public/seer/xi/`：立繪、頭像與屬性圖示。

### 5. 新精靈交付清單

- [ ] 原始描述已保存。
- [ ] 資料與技能可在 UI 顯示。
- [ ] 每條描述已標記執行方式。
- [ ] 所有新共用規則有核心測試。
- [ ] 專屬效果有正向、反向與邊界測試。
- [ ] 舊 localStorage 資料不會覆蓋新版權威內容。
- [ ] 首頁、編輯頁、百科、命運之輪與戰鬥頁顯示正確。
- [ ] P1/P2 立繪方向、頭像、背景與屬性圖示正確。
- [ ] `lint`、`test`、`build` 通過。

## 七、製作 EXE 的建議流程

### 階段 1：補齊封裝工具

在確認目前功能版本可發佈後，安裝固定版本的開發依賴：

```powershell
npm install --save-dev electron electron-builder
```

安裝後提交 `package.json` 與 lockfile。不要只在某台電腦全域安裝。

### 階段 2：設定產品資訊

至少調整：

- `package.json` 的正式名稱與版本，例如 `1.0.0`。
- `electron-builder.yml` 的 `appId`、`productName` 與輸出名稱。
- Windows `.ico` 圖示。
- 版權、發佈者與說明。

每次公開版本只能提高版本號，不可用相同版本覆蓋不同內容。

### 階段 3：先驗證 Electron 開發版

```powershell
npm run lint
npm test
npm run build:electron
npm run electron:dev
```

至少操作：首頁、精靈詳情、編輯、開始戰鬥、技能、換人、道具、結算、重新開啟與資料保存。

### 階段 4：產生安裝版與 portable EXE

```powershell
npm run package:electron
```

依目前設定，預期產生：

- NSIS 安裝程式：供一般玩家安裝。
- Portable EXE：玩家直接雙擊即可執行，外部不需另外放 Node.js 或專案資料夾；Electron 會在執行時自行處理內含資源。

玩家不需要先把圖片壓縮一次、再連同 EXE 壓縮。圖片應由建置流程直接包含在應用程式資源中。若要上傳 Google Drive，只需將最終 EXE 或包含說明與雜湊的發佈 ZIP 上傳。

### 階段 5：乾淨環境驗收

不可只在開發電腦測試。至少使用一個沒有 Node.js、沒有專案原始碼的 Windows 帳號或虛擬機驗證：

- EXE 可啟動。
- 不需要額外資料夾。
- 所有圖片、屬性圖示與字型可讀取。
- 儲存資料的位置可寫入。
- 關閉視窗後本機伺服器行程會結束。
- 防火牆、SmartScreen 與防毒軟體的行為可接受。
- 中文路徑與非系統管理員帳號可正常使用。

### 階段 6：產生發佈資訊

每個版本至少附上：

- 版本號。
- 發佈日期。
- EXE 檔名與大小。
- SHA-256 雜湊。
- 更新內容。
- 已知問題。
- 最低 Windows 版本。

Google Drive 適合做人工下載鏡像，但不適合作為唯一的自動更新來源。自動更新建議使用 GitHub Releases 或可直接下載的 HTTPS 伺服器，提供機器可讀的版本 manifest、檔案雜湊與簽章。

## 八、正式發佈前的阻擋條件

- 資源必須依賴專案原始資料夾才能載入。
- 沒有版本號與雜湊。
- 更新機制會直接覆蓋執行中的程式，且沒有回復方案。
