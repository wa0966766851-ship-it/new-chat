# 出招動作機制解析（以聖靈譜尼為例）

> ⚠️ 2026-11-05 複核：本文含未經證實的推論，只供歷史參考。`petClipPool.ts`、512 MiB 與 Worker 是本專案／第三方工具的做法，未證明是官方 U 端策略；單一矩形也能逐幀換圖，多頂點網格不能證明動作自然；命中前的所有影格不能全部稱為蓄力。後續依 `docs/guides/自製動畫重製規格_20261105.md` 查看實際姿勢與時間軸。
>
> 建立：2026-11-04
> 資料來源：`src/battle/petAnimationAssets.ts`、`node_modules/@seer-pet-anim/swf-bundle`
> 目的：解釋「出招動作」與「待機」的差異，以及官方如何處理大量幀

## 一、關鍵發現：出招動作的資料結構完全不同

### 待機（standby）＝ 序列帧

```
每幀 = 1 個矩形（8 個頂點數 + 4 個 UV 數）
資料量 = 27 幀 × 12 個數 = 324 個數
```

### 出招（attack）＝ 逐幀網格

```ts
interface SwfFrame {
  labels: string[];
  mesh: SwfFrameMesh;
}

interface SwfFrameMesh {
  positions: Float32Array;   // 頂點位置
  uvs: Float32Array;         // UV
  addColors: Float32Array;   // 加法混合色
  mulColors: Float32Array;   // 乘法混合色
  indices: Uint16Array;      // 三角形索引
  subMeshes: SwfSubMesh[];   // 子網格
}
```

**每幀都是完整網格，與我失敗的方案同構。**

## 二、為什麼官方這樣做卻不會爆

### 官方譜尼的完整數據

| 序列 | 幀數 | 說明 |
|---|---|---|
| standby | 27 | 待機 |
| **attack** | **173** | **出招（最長）** |
| sa | 70 | 特殊攻擊 |
| cp | 50 | 蓄力 |
| hited | 8 | 受擊 |
| **合計** | **328 幀** | |

**atlas：8192×8192 = 256 MB（RGBA 未壓縮）**

### 官方怎麼處理 256 MB

**關鍵：`petClipPool.ts` 的 LRU 回收機制**

```ts
limitBytes: 512 * 1024 * 1024,   // 最多同時快取 512 MB
idleBytes:  32 * 1024 * 1024,    // 閒置時只保留 32 MB
idleMs:     15000,               // 15 秒後回收
handoffMs:  250,
```

**運作方式：**

1. **不是一次全部載入** — 只載入當前需要的精靈
2. **超時回收** — 15 秒沒用就釋放
3. **預算上限** — 超過 512 MB 就淘汰最久未用的
4. **Web Worker 解析** — `parseBundleInWorker` 避免阻塞主執行緒

### 為什麼我的方案不行

| 項目 | 官方 | 我的方案 |
|---|---|---|
| **圖集格式** | 二進位 `.pet`（SWF 包） | JSON + PNG |
| **頂點資料** | `Float32Array`（二進位） | JSON 陣列（文字） |
| **資料位置** | 打包在 bundle 內 | 獨立 41.9 MB JSON |
| **記憶體管理** | LRU 池 + Worker | 一次性載入 |
| **解析** | Worker 非同步 | 主執行緒同步 |

**同樣是逐幀網格，官方用二進位 + 池化 + Worker，我用 JSON + 一次性載入。**

## 三、出招動作的具體機制

### 為什麼出招需要逐幀網格

**待機只有整體縮放（1 個矩形就夠）。**

**出招需要：**

| 需求 | 為什麼需要網格 |
|---|---|
| **武器揮動** | 不同部位的變形程度不同 |
| **身體扭轉** | 軀幹與四肢要分別變形 |
| **特效跟隨** | 光效要附著在武器上 |
| **多層次** | 本體 + 武器 + 光效各自獨立 |

**單一矩形無法表達這些變形，必須用網格。**

### `subMeshes` 的作用

```ts
interface SwfSubMesh {
  // 每個子網格對應一個材質（本體／武器／光效）
}
```

**一個角色被切成多個子網格，每個子網格用不同材質：**

- 本體：normal 混合
- 光效：additive 混合
- 影子：multiply 混合

**這解釋了 `addColors` / `mulColors` 的用途：逐頂點的顏色混合。**

### `hits` 的作用

```ts
attack: { frames: 173, hits: [138] }
```

**`hits: [138]` = 第 138 幀是「命中判定點」。**

**出招動畫 173 幀中，前 138 幀是蓄力與揮動，第 138 幀才真正打到對手。**

**這就是「出招」與「待機」最大的不同：出招有明確的時間軸與命中點。**

## 四、我的方案到底錯在哪

### 錯誤 1：用 JSON 存二進位資料

```
官方：Float32Array → 直接寫入二進位 buffer
我的：Float32Array → JSON.stringify → 文字
```

**JSON 序列化浮點數會膨脹 2-3 倍，且解析極慢。**

### 錯誤 2：一次性載入

**官方有 LRU 池（512 MB 上限、15 秒回收），我直接全載。**

### 錯誤 3：網格密度過高

```
官方：依部位需求決定（武器處密、身體處疏）
我的：全圖統一 48×62
```

**官方是「選擇性細分」，我是「平均細分」。**

### 錯誤 4：沒有用 Worker

**官方用 `parseBundleInWorker`，我在主執行緒解析 41.9 MB JSON。**

## 五、正確的做法（如果要做出招動作）

### 方案 A：用二進位格式

```
把 positions/uvs/indices 寫成 Float32Array/Uint16Array
存成 .bin 檔，用 fetch + ArrayBuffer 讀取
```

**預期：41.9 MB → 約 12 MB（3.5 倍壓縮）**

### 方案 B：選擇性細分網格

```
武器／手部：16×16
軀幹：8×8
背景／靜止部分：1×1
```

**預期：2,867 quad → 約 400 quad（7 倍減少）**

### 方案 C：分離靜態與動態

```
靜態部分（不變的部位）→ 序列帧（UV 平移）
動態部分（會變形的部位）→ 網格
```

**這是官方實際做法：待機用序列帧，出招用網格。**

### 方案 D：用現成的官方素材

**如果精靈有官方 `.pet`，直接用 `petAnimationAssets.ts` 的方式接入。**

**只有自製精靈才需要自己生成動畫。**

## 六、官方與自製的完整對照

| 項目 | 官方（譜尼） | 官方（六刃自製） | 我的失敗方案 |
|---|---|---|---|
| 格式 | `.pet` 二進位 | manifest.json + atlas | manifest.json + atlas |
| 待機 | 網格（27 幀） | 序列帧（32 幀） | 網格（40 幀） |
| 出招 | 網格（173 幀） | 序列帧（38 幀） | 網格（60 幀） |

**注意：官方的 `wuxu_liuren`（自製）也只用 19 KB，因為它是純序列帧。**

## 七、結論

### 出招動作的三種實現層級

| 層級 | 技術 | 資料量 | 適用 |
|---|---|---|---|
| **1. 序列帧** | UV 平移 | 最小（KB） | 待機、簡單動作 |
| **2. 逐幀網格** | 每幀完整網格 | 中（MB） | 出招、複雜變形 |
| **3. 骨骼蒙皮** | 骨架 + 權重 | 小（KB） | 3D 遊戲 |

**官方用「1 + 2」，我用「2 但沒優化」。**

### 對自製動畫的建議

**如果只有序列帧素材：**
→ 用層級 1（UV 平移），19 KB 就能跑

**如果要做出招的複雜變形：**
→ 用層級 2，但必須：
1. 二進位格式（不用 JSON）
2. 選擇性網格細分
3. LRU 池化
4. Worker 解析

**絕對不要：**
→ 用 JSON 存 2,867 個 quad × 182 幀
