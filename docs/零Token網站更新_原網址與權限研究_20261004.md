## 結論與目前界線

目標是固定程式自動完成建置、校驗與發布，不呼叫 LLM。這裡的「零 token」指不消耗 AI 推論 token；GitHub 授權憑證、網路流量、CI／託管額度是另一回事。

原網址仍有值得驗證的改造方向，尚不能把它判為不可行。本輪沒有改動線上網站、分享名單、排程，也沒有新建網站。若原網址的改造與授權驗證失敗，才使用新網站作備案；再新建一個相同架構的靜態 Sites 快照，不會自動解決 GitHub 更新問題。

## 優先研究的原網址方案

一次性把 Site 從「固定快照」改成「受原分享限制保護的固定版本供應器」。之後 GitHub 的普通 CI 建置新版本，版本供應器讀取通過驗證的內容，而不是每次叫 AI 重做部署。

概念流程：GitHub 提交 → 固定測試與建置 → 不可變版本套件 → 受保護的網站供應器 → 玩家手動檢查與載入。

Cloudflare Workers 能以普通 HTTP 程式取得外部內容，這可作為原網址改造的技術基礎；但「能 fetch」不等於此 Site 的整條鏈已實裝或驗證。需完成以下項目才可上線：

1. 驗證此 Site 可由靜態快照升級為 Worker，保留同一 project／網址／custom 分享名單。
2. 確認內容來源。若建置檔放在公開 GitHub 分支或公開附件，任何人可讀取檔案，不能宣稱素材保密；保留入口登入不等於公開上游也受同樣分享限制。
3. 若要求上游內容也私密，需私有物件儲存或私有建置來源，以及伺服器專用授權。尚未配置，不得把短期 Sites 憑證、個人金鑰放在前端。
4. 所有入口、JS、CSS、圖片、資料與版本 API 都要走同源受保護路由。不得只保護首頁，再 iframe 一個可匿名遊玩的網站。
5. 使用不可變 buildId 及逐檔 hash；先上傳並校驗整包，再原子切換目前版本。保留舊版與舊動態模組，避免戰鬥中的頁面載不到舊資源。
6. JS／CSS 相對匯入及 `/seer`、`/elf-art`、`/images`、特殊模式資料路徑須逐一驗收。不能只確認首頁顯示。
7. 供應器只讀固定本專案來源，不接受使用者任意 URL，不轉送訪客 Cookie、登入資訊或平台授權標頭給上游。
8. 更新失敗仍供應上一個已確認版本。必須驗證快取隔離、版本回滾、未登入拒絕、受邀者可讀但不可發布。

這些是待驗證的改造計畫，不是已完成的部署功能。

## 已準備的不用 AI 建置流程

`.github/workflows/build-web-package.yml` 僅提供 `workflow_dispatch`。目前只有讀取權限，沒有網站部署權限，也沒有自動 push 觸發。

順序：安裝鎖定依賴 → lint → 完整測試 → build → bundle 稽核 → 準備靜態套件 → 逐檔校驗 → 上傳 Actions artifact（30 天保留）。不呼叫 Gemini／OpenAI API。

`scripts/prepare_web_package.mjs` 排除 Express 的 `server.cjs`、原始碼映射、`.vite` 建置索引與敏感路徑，補上 Express 原本獨立供應的 images，產生 `web-package-manifest.json`。本機 539 檔逐一核對通過。

GitHub 自動發給工作流程的 `GITHUB_TOKEN` 是授權憑證，不是付費 AI token。現行流程不要求把個人 PAT 放進瀏覽器。流程未推送之前，管理中心的 Actions 連結不能當作已啟用服務。

## 新網站備案

- GitHub Pages 能由 GitHub Actions 直接部署，但不能把普通公開 Pages 站當作現有 Sites 私密分享的等價替代。
- 若新站也需受限分享，必須選擇並配置支援登入／邀請控制的託管方式，再驗證原站受邀者如何取得權限。需要對應託管帳號權限，不能猜測已有憑證。
- 若只是建立另一個 Sites 靜態快照，未接通版本供應器或正式 CI 接口，仍有相同更新瓶頸。
- 更換來源會改變瀏覽器本機存檔作用域，需先匯出精靈／背包／進度並驗證匯入，不能保證換網址後自動看見原存檔。

## 下一階段驗收門檻

保留原網址原型必須實證：沒有 AI 呼叫、相同網址、現有分享限制、完整資源載入、舊戰鬥不受更新打斷、損壞包不切換、斷線仍可讀上一版、回滾與玩家存檔不變。未通過前保留目前 Site 第 9 版，不啟用暫停排程。
