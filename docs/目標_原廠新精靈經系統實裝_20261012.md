# 目標：從原廠抓一隻現代複雜精靈，只經自訂系統實裝（2026-10-12）

## 目標定義（完成的條件）

1. 資料由 API 取得：**SeerAPI**（`https://api.seerapi.com/v1`，官方 Unity 客戶端資料，本專案技能石與圖片已在用）為準；BWIKI MediaWiki API 只補攜帶欄位（先手／防御／强化／制敌／第五）與一般技能池。原始回應存檔並以 SHA-256 與瀏覽器端比對。
2. 精靈資料只經「描述 → 煉成（distillEffect）→ 連鎖 Kit」執行，**不寫任何專屬 handler**，`BattleScreen.tsx`／`battleEngine.ts` 不出現精靈名稱。
3. 魂印與 5 個攜帶技能的每一句都有 P1／P2 語意測試；用到的新機制全部是通用 op／條件／事件（附參數合約與測試）。
4. lint、完整測試、build、audit:bundle 全過。

## 選定精靈：4937 星光·雷納多（機械，總和 740，2026-08 上線）

- 選擇理由：近期上線、機制複雜（雙方使用技能時觸發、本場累積增傷上限、恢復溢出換算減傷與護盾、護盾存續期間被攻擊觸發、護盾消失觸發、能力提升保護、每回合能力提升…），而且**所有名詞都在描述內自洽**，不依賴 wiki 未定義的系列資源。
- 另外看過的候選：4947 不滅戰魂·蓋亞、4946 萬霆神律·雷伊。它們依賴「武道／不武／勝之道」「辰律／雷辰」等系列資源，wiki 沒有定義，需要使用者另外提供規則，所以不選為第一隻。

## 為此新增的通用機制（2026-10-12）

| 類別 | 內容 |
|---|---|
| 句型 | 「技能使用成功時，N%改變自身／對手X等級±M」；無標記的開頭「必中」「先制+N」（技能欄位同意時才視為固有）；「回覆」＝「恢復」；「攻擊+1、防禦+1…」數值相同的列舉；「自身解除所處的異常狀態」；省略主詞的「體力低於對手」；「若屬性相同」（本系） |
| 條件 | `stab`（本系）、`dmg_cmp`（結算後的傷害比較，只限命中後事件）；消除後的「若對手不處於…」改用使用前快照（`pre`） |
| 計數 | `per`：`self_up_kinds`（自身能力提升種類數）、`sides_priority_zero`（本回合先制為0的方數；引擎在排序時記錄 `actionPriorityThisTurn`） |
| 動作 | 威力加值 `boost{power,add}`（引擎 `powerAddThisAction`，先加再乘倍率）；`invalid_turns{next}`（下N回合技能無效，回合型不再被一次消耗）；`watch{trig:'shield_broken'}`；`stat_protect_turns`（能力提升不可消除／吸取，吸取整體失敗）；`ignore_next`（下次攻擊無視攻擊免疫）；`heal_reduce_turns`；`heal_overflow`（恢復溢出換算下回合受攻擊減傷與護盾）；`battle_boost`（本場戰鬥累積攻擊增傷，上限，跟著精靈保留） |
| 觸發 | 魂印「雙方使用技能時」＝自身使用技能時＋對手使用技能時；「…，護盾存在期間自身每次受到攻擊後Y」拆成「受到攻擊時＋自身有護盾」子句 |
| 引擎事件 | `SHIELD_BROKEN`：在場精靈護盾由有變無（打破或消除）時派發給持有方（每個效果結算後檢查） |
| 匯入／煉成 | `scripts/import_seer_wiki.ts`（SeerAPI 覆蓋）、`scripts/build_imported_kits.ts`（預先煉成，只收 complete）、`scripts/audit_imported_elf.ts`（缺口清單） |

## 解讀與待確認
- 「護盾存在期間自身每次受到攻擊後消除對手能力提升狀態」：視為常駐（任何護盾），不限魂印本身給的護盾；判斷時點為受擊後（這次攻擊打破護盾則不觸發）；條件目前也把護罩算進「護盾」。
- 「1回合內對手體力恢復效果減少100%」＝當回合（回合結束到期）。
- 魂印 BOSS 無效（SeerAPI 標示）已記在資料 `bossInvalid`，引擎尚未讀取。
- 技能池的「屬性複製」（5回合內使自身屬性與對方相同）尚無通用機制，未放入技能池。
- 魂印沒有名稱（SeerAPI／wiki 都沒有），暫用「魂印」。

## 延後載入（2026-10-12）

**使用點盤點**：`DEFAULT_ELVES` 在 App／StartScreen／ElfEditor／MassTestModal／TestRunnerPage／GameDataContext（經 `GLOBAL_ELVES`）／clauseBreakdown 與多個測試、稽核腳本使用；皆為同步讀取同一個陣列。

**做法（最小改動，不改戰鬥行為）**
- `src/data/defaultElves.ts` 不再靜態匯入 `importedElves.ts`。`DEFAULT_ELVES` 仍是同一個陣列物件；新增 `loadImportedElves()`（動態 `import('./importedElves')`，重複呼叫共用同一個 Promise），完成後以與其他精靈相同的流程（`applySourceText` → `applyReviewedSkillKits` → 定稿）追加到清單**尾端**（順序、`id`、數值與先前靜態載入完全相同），並通知 `subscribeDefaultElves` 的訂閱者。載入完成前清單不含匯入精靈。
- `src/main.tsx` 在**首次繪製前**呼叫 `loadImportedElves()`（失敗只警告，以不含匯入精靈的清單繼續），完成後才 `createRoot().render`；`GameDataProvider` 只訂閱（`subscribeDefaultElves`），清單變動時重算 `allElves`。`GLOBAL_SKILLS` 同步補齊。不可改成掛載後才載入：StartScreen 的 `useEffect([allElves])` 隊伍同步會在 `allElves` 換身分時，用圖鑑預設覆蓋已存隊伍的自訂銘文（曾使 battlePresentation 測試失敗）。
- 測試／稽核腳本沒有首頁載入量問題：改引用 `src/data/defaultElvesLoaded.ts`（`export * from './defaultElves'` 後 `await loadImportedElves()`）。**應用程式不得引用此檔**（頂層 await）。
- 鎖定：`tests/importedElvesLoading.semantic.test.ts`（靜態匯入圖不含匯入模組／打包檔；載入前清單不含、載入後只追加一次且在尾端、訂閱通知、`GLOBAL_SKILLS` 補齊、Provider 載入後 `allElves` 含 `wiki_4937`、main.tsx 先載入再繪製）；`scripts/audit_bundle.ts`（首頁初始區塊不得含匯入精靈模組字串，且匯入精靈必須是獨立的動態區塊）。

**已知影響**
- 首次繪製會多等一次動態載入（小型區塊，非阻塞主 bundle 解析）。
- 之後每匯入一隻只增加延後載入區塊（約 +8 kB），不再增加首頁初始 JS。

**首頁初始 JS**：964,196 → 955,102 bytes（匯入精靈）→ 938,380 bytes（再把 `stagedArenaElves.ts`＋`docs/spirit-arena/heavyweights.json` 併入同一次 `loadImportedElves()`，順序維持「競技場精靈 → 匯入精靈」追加在清單尾端）。`audit:bundle` 預算已由 960 kB 降為 950 kB（餘裕約 11.6 kB）。使用者 2026-10-12 授權以延後載入處理；效果呈現層（effectPresentation）維持原狀。
- 影響：階段競技場精靈與匯入精靈一樣，在 `loadImportedElves()` 完成前不在 `DEFAULT_ELVES`；測試／稽核腳本經 `defaultElvesLoaded` 取得完整清單（直接 import `defaultElves` 的程式需自行等待）。`stagedArenaElves` 本身仍可直接匯入（`src/tests/stagedArena.registry.test.ts` 等）。
