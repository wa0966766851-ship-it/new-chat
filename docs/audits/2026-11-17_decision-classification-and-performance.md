> 後續更新（2026-11-18）：採逐項執行及限定記憶體上限後，全專案型別檢查與桌面正式建置／HTTP啟動驗證已完成，啟用版本為1794938149576，包含本報告所述載入修改。OFM／DSH舊程序的終止及未完成壓縮檔刪除仍未執行；下文環境失敗段落保留當時狀態。介面本輪修改與驗證見[後續報告](2026-11-18_skill-availability-and-dance-targets.md)。

## 結論

決策模型適合當「既有積木的分類／候選排序助手」，目前沒有必要將它設成建立自訂精靈的必經步驟。它能減少找積木與確認分類的人工操作，無法取代本地效果語義、參數驗證與戰鬥執行器；也不會因此移除動畫、Electron、備份或套件所占的空間。

本輪完成靜態架構與磁碟盤點、低風險載入改善，以及有逐檔校驗的備份封存。未新增自動分類 API、未用私人自訂精靈呼叫收費模型、未測得分類準確率或對戰勝率提升。

## 從模型性質開始

目前接入的是 `server/battleAI/geminiDecision.ts` 的 `gemini-decision-1`：以 `/v1beta/decisions` 傳入局面與合法候選，要求選擇一個 action。它是針對固定答案評分的雲端模型，回傳選項、機率與信心；不生成答案文字。官方列出單選 2–255 選項、每次最多 1,000 個獨立問題。[官方模型說明](https://aistudio.google.com/docs/models/gemini-decision-1)

因此可以把「該句屬於傷害／恢復／資源／狀態哪類」、「是否需要離場清除」作為獨立判斷；不能要求它直接產出任意數值、完整巢狀 Kit、程式碼或說明文字。問題間不能讀取彼此答案；有依賴的判斷應分階段執行，或在本機合成。[官方 Decisions API](https://aistudio.google.com/docs/decisions-api)

一般生成模型搭配 JSON Schema 才適合輸出數值與完整物件；即使 JSON 格式正確，仍需由程式檢查數值與語義。[官方 Structured Outputs](https://aistudio.google.com/docs/structured-output)

分類服務不等於遊戲規則引擎，也不表示它從每次對戰／使用者修改中自動更新模型權重。若要保留修正，應保存本地已確認的對照資料及版本，不把模型的信心當成遊戲機制已正確實裝。

## 目前已有什麼

| 層次 | 現有來源 | 功能與邊界 |
|---|---|---|
| 文字分詞 | `src/utils/effectParser.ts` | 本機時點／條件／動作等分類，給編輯介面預覽 |
| 模板建議 | `src/utils/aiTextParser.ts`、`src/data/cardTemplates.ts` | 既有關鍵字與範本比對；可呼叫後端，失敗退本機 |
| 雲端生成 | `server.ts` 的 generate-elf、analyze-elf、parse-effect-text、dissect-tokens | 目前使用一般生成模型與 Schema；不能與決策端點混為一談 |
| 積木與搜尋 | `opCatalog.ts`、`codexRegistry.ts`、`blockLibraryData.ts` | 分別有操作分類／編號／骨架資料與既有搜尋，不需要先重造一套全文百科 |
| 實際執行 | `src/blocks/registry.ts`、`runtime.ts`、effects 註冊表 | 決定觸發、數值、目標、免疫與結算次序，必須保留 |
| 決策 API 金鑰 | `server/battleAI/` | 本機防護及使用者加密保存；舊文字生成仍是另一條設定路徑 |

目前 `OP_CATALOG` 有 647 個紀錄，含內部、條件及相容項目；不是 647 個可隨意互換的可用動作。11 個 family 中，傷害 134、流程／特殊 159。整個目錄超過單次單選 255 上限，應先做本地篩選或分層分類。既有 EffectCode、骨架 ID 與 op 名稱也不是同一命名空間。

注意本機模板比對包含示意性的預設數值與效果類型。例如單純看到「強化」「吸取」不能保證預設能力等級／比例就是原文意圖。模型建議不應讓這種近似映射直接變成正式機制。

## 建議的實作架構（本輪研究提案，尚未接入）

1. 保留原文與階層，建立來源範圍及句子 ID；先用本地解析取出明確數值、單位、時點與目標。
2. 使用現有分類／搜尋擷取少量候選（例如前 20 個）與「未知／沒有符合項目」，不將全部源碼或完整精靈庫送上雲端。
3. 使用者主動開啟分類協助後，才透過本機受保護端點呼叫決策模型。每個問題明確帶入原句和候選說明；模型只回傳受允許 ID、機率及信心。
4. 條件、目標、時點、離場清除各自分類；多效果句不能只取一個主效果。先後有依賴的問題分兩階段，最終由本機合成草稿。
5. 本機驗證 ID、欄位範圍、P1／P2 作用域、分支與觸發順序。未知效果留待確認，不以最像的現有積木冒充。
6. 預覽對照「原文 → Tokens → 積木草稿」，確認後才加入；不自動覆寫已實裝 Kit。
7. 快取鍵包含原文雜湊、目錄／Schema／提示版本；修改原文或目錄即失效。只保存必要分類資料，不保存金鑰；可清除。

分類設定與對戰 Gemini 開關應分開，方便只使用本地自訂工具。可以共用既有後端金鑰保護，但不能把金鑰放進前端、圖紙、分類快取或 Git。失敗、逾時或沒有金鑰時，原有本機分類與手動積木仍可用。模型呼叫只發生在編輯時，不能放進每幀渲染或戰鬥事件熱路徑。

## 可行性與必要性判斷

| 工作 | 適合程度 | 原因 |
|---|---|---|
| 既有積木大類與候選排序 | 高 | 固定選項與評分符合模型介面 |
| 時點、對象、是否離場清除 | 中 | 原句有足夠資訊時可協助；否定、例外仍需驗證 |
| 整句多效果與巢狀分支 | 部分 | 先保留階層及來源，再分解問題；單選不能涵蓋多個行為 |
| 任意數值／公式／新印記定義 | 低，不能單靠它 | 決策模型不負責生成任意欄位；本地抽取或生成模型仍需驗證 |
| 新增未知機制的執行碼 | 不適合直接交付 | 需要新的通用積木、型別、事件接點及實戰測試 |
| 取代 Blockly／本地執行器以縮包 | 不建議 | 會失去離線可編輯性、規則可重現性，磁碟主因也不在此 |

先以人工確認過的資料建立保留測試集，再比較「本地既有分類」與「本地候選＋模型排序」。至少分別量測操作 ID、時點、目標、否定條件、數值及巢狀分支，不只看分類大類。加入造成／受到、首次命中／每次用技、真實／固定／百分比傷害、技能無效／附加失效／抵擋傷害、離場保留／清除等反例；採 P1／P2 數值測試確認實際機制。另記延遲、費用與拒答率，調校信心門檻後才能決定是否減少人工確認。

目前並無這批實測結果，所以只能判斷架構可行，不能宣稱它比本地分類更準、能取代現有程式或必須導入。

## 封存與還原

新增 `scripts/maintain_local_workspace.py`。預設只產生計畫，`--apply` 才處理固定範圍：舊鬆散備份、動畫備份、歷史 web-package、舊測試文字紀錄，以及未在執行的舊 Electron 建置暫存。會拒絕版控檔、連結、24 小時內變動資料及執行中來源。先 ZIP64 壓縮、逐檔 SHA-256 讀回，再檢查來源與啟用版本未變，才刪除原鬆散目錄。

```powershell
py scripts/maintain_local_workspace.py
py scripts/maintain_local_workspace.py --apply
py scripts/maintain_local_workspace.py --restore .local-archives/maintenance-20261117/_backup_ui.zip
```

備份位於 `.local-archives/maintenance-20261117/`，內含 `_archive/manifest.json`。還原到新的 `build/restored/` 目錄，保留原相對路徑，不覆寫目前專案。回執在 `.cleanup-audit/maintenance-20261117-result.json`；如中斷，已核對完成的 ZIP 可協助恢復流程。大型歷史 ZIP、正式安裝器、動畫素材、玩家存檔、API 金鑰、Git 歷史與父資料夾其他專案不在清理範圍。
