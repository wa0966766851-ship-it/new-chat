## 第二次截圖後的補查（前一輪驗收範圍不足）

使用者第 11 回合畫面仍只有逐回合篇數，死亡者保留原體力上限，紀錄含「次元龍帝臨世」。此字串只存在舊專屬 handler，證明那場戰局有執行舊路徑；未取得該瀏覽器存檔，不能斷言其完整內容或當時載入版本。

新增失敗測試確認漏網形式：Git `6bfd57b` 實際發布的單項 `legacy_handler` 包裝。上一輪只辨認 Git `70ec3f4` 的真正積木，非空包裝會被保留，又被路由器導回舊 handler；舊 handler 沒安裝通用死亡轉交規則，所以能逐回合增加篇數卻不轉交。

修正：精確辨認已發布包裝、正式原文由同一舊包裝器生成的版本、頂層舊包裝，以及無積木但明確指定 registry 的已知舊定義。轉為當前正式積木；玩家改過的原文／參數及受保護定義維持原樣。沒有新增戰鬥主流程的精靈名稱判定。

新增驗收：

- 真實 GameDataProvider + StartScreen 同時載入舊倉庫覆寫與舊背包，兩側進戰資料均為實際 kit，含 `snapshot_resource_rule`。
- 真正舊積木、歷史包裝、正式原文包裝、頂層包裝、明確 registry 舊版，各測 P1／P2 與同側／對側後備次元龍接收。原持有者消逝、maxHp=0；接收者篇數、快照與體力上限一起增加。
- P1／P2 各連續三隻持有者死亡，體力依序1000、2000、3000；次元龍初始10000。接收後篇數依序2、5、9，體力上限11000、15000、24000。保留每篇取得當下體力，沒有用目前體力或回合數冒充轉交量。
- 檢查戰鬥紀錄不得出現舊 handler 的「次元龍帝臨世」。
- 桌面更新流程加入舊背包入口、死亡轉交及28組次元龍機制檢查，失敗不啟用新版本。

這些是程式與正式入口回歸測試結果，並非使用者截圖那場已進行中戰局的修復證明。應以新建戰局驗收；已丟失的歷史體力快照不能憑畫面猜回。

## 正式規則

- 初始出戰、待命、選禁候選都是正常精靈；效果額外加入的精靈才有額外身分。不能用排列位置判斷。
- 背包存檔保存陣容順序與實例身分；下次開戰的配置與效果取目前精靈倉庫，透過既有來源校正取得最新內建定義，保留玩家修改的定義。
- 詩章獨立記錄取得當下的體力上限；死亡轉交後依既有「消逝」規則處理原持有者，體力記錄與詩章交給存活次元龍。
- 告命詩途首次命中建立五回合效果，之後每次使用技能吸取，沿用既有回合類積木。

## 查到的問題與修正

1. 巔峰準備把第 pickCount 隻之後都標為額外，還存回背包。移除這個寫入來源；組隊、草稿、舊紀錄與待命快照都清理舊身分。戰鬥中真正召喚的額外精靈不經這個清理。
2. 畫面與存活統計另用「第七隻以後」猜額外身分。改為讀取正式身分；換人及勝負測試包含正常精靈位於後方的情況。
3. 準備畫面逐欄同步副本，漏掉頂層積木、特質等資料；重新載入舊紀錄又可能沒有觸發同步。統一使用 prepareSavedBattleRoster，倉庫或隊伍變更即同步完整定義，不需移除重放。
4. 已發布的次元龍舊非空積木不會被空值補齊流程修正。加入精確歷史版本校正，來源為 Git 70ec3f4c8406867594d25b950e68a684b91a56e6 的 reviewedKits。只遷移完全匹配的已知舊魂印／告命詩途；未知或玩家修改的積木不覆蓋。
5. 詩章同步先合併指定持有者，又用單隻精靈的印記覆蓋全側，會清掉後備精靈的體力記錄。移除整側覆蓋，沿用既有 UPDATE_ELF 的持有者合併。

精靈效果仍由有效積木安裝通用規則，沒有在 BattleScreen 主檔或引擎加入次元龍特判。
