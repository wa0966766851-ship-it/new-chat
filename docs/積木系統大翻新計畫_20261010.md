## 1. 目標（完成的定義）

1. **只有一種中間表示**：連鎖子句（Clause → Stmt → Act，`blocks/model.ts`）。Kit 是「每句一個 `effect_sequence`」的清單。Kit 原子只作為舊存檔的讀取轉換，不再產生。
2. **只有一個執行器**：`runClause`（`blocks/runtime.ts`）。
3. **op 是通用的**：每個 op 都有參數合約、讀取端，以及 P1/P2 語意測試。精靈專屬機制（印記、異能值、星執、詩章、符文、咒怨…）一律抽象成**通用資源 op**（具名計數器加門檻事件），不在 op 內寫精靈名稱。
4. **戰鬥中不猜文字**：`genericSkillText` 和描述即時解析退出戰鬥路徑。描述只在編輯時煉成定義，並存下 `sourceSha256`；原文變更時標為過期。
5. **handler 只剩過渡期**：一份定義 100% 轉成連鎖並通過測試後，刪除該定義的 handler 分支。最終 `elves/*/registry.ts` 只剩資料或空殼。
6. **「已驗收」只能由語意測試決定**，不能用解析率決定。

## 2. 不變的規則

照 `docs/下一位AI接手指南_342效果定義與發布_20261009.md` 的 §3（禁止事項）與 §5（使用者確認規則）。另外新增三條：

- **上下文規範**：`BattleEventContext` 不得用 `{...ctx}` 複製，一律用 `Object.create(ctx)` 再覆寫。
- **快照規範**：「寫入後比對」必須先複製寫入前的值（`updateElf` 可能原地修改物件）。
- **哨兵值禁用**：不用 99 之類的數字代表「全部」，改用明確的 mode（例如 `recover`）。

### P2 擴充連鎖合約：把已實作的 op 升格（解鎖約 250 句）

依 §0.2 的 B 類順序，一次升格 1～3 個 op：

| 順序 | op | 做法 |
|---|---|---|
| 1 | `noop`（先制／必中標記） | 改成 `skill_property` 查詢（已有），不要放行 noop 本身 |
| 2 | `prio_turns` | 參數 side／v／turns／next；確認先制計算有讀取 |
| 3 | `immune_status_turns`、`immune_status_count`、`immune_statdown_turns`、`immune_attack_count` | 合併成一個 `immune` op（kind＝status／statdown／attack；期限＝turns 或 count；cls 分類） |
| 4 | `vampire` | 依已確認規則：等量＝本次攻擊傷害 |
| 5 | `mark`、`mark_turns` | 等 P3-5 通用層數資源完成後再升格 |
| 6 | `pp_zero`、`at_round_end`、`dmg_cap_turns`、`crit_turns`、`dmg_taken_x2`、`pp_cost_mult` | 逐一處理 |
| 7 | `rampInc` 參數 | 加入 dmg／heal 等的參數合約 |
| 8 | `custom`、`note` | **不放行**，依 P0-3 的盤點逐句改寫 |

每升格一個 op 都要做到：

- 在 `SEQUENCE_ACTION_FIELDS` 加入欄位與型別檢查。
- 確認有讀取端（查 P0-4 的表）。
- 寫測試，矩陣如下：P1/P2、條件成立與不成立、成功與失敗分支、封附加、期限到期、換人、傷害分類。

觸發與條件缺口（C 類約 60 句）在這一階段一併補：先把缺的事件或查詢列出來，每個都要有派發點與測試。

### P3 新通用機制（處理 745 句無法解析）

依影響句數排序。每個機制的流程固定：設計合約 → runtime op → **錨定整句**的解析規則（不得吞半句）→ 測試。

1. **次數型期限「下N次」**（49）：通用的使用次數計數器，消耗時點可指定為「攻擊」「受擊」「使用技能」。不可和回合期限混用。
2. **N回合內的增減傷、免疫、限制**（116，與其他群重疊）：統一使用 `addTimerTo` 的 payload 與 `activeConstraints` 讀取，不新增零散鍵。
3. **傷害上限與限制**（44）：「無法超過N點」「傷害減半」「無視限制改為…」。放在傷害計算節點，依分類（攻擊、固定、百分比、真實）分開處理。
4. **秒殺與擊敗**（39）：秒殺 API 要能被免疫、護盾、存活效果攔截，並有「下次被擊敗時」事件。
5. **印記與層數**（25，加上 B 類 mark）：通用層數資源，包含上限、施加方、持有方、到期、清除、場下保留。
6. **系統資源**（30，加上 custom 的 c 類）：異能值、星執、詩章、符文、咒怨、命運之輪改用「具名資源加門檻事件」。各精靈的資料只填名稱、上限與門檻效果，不寫程式。
7. **場下與下一隻登場**（40＋11）：場下鉤子（benchSkip 的白名單）與 `nextElf*` 消費。
8. **護罩與護盾分離**（25）：護罩另立資源，和護盾不可互相代替。
9. 其餘：異常、能力等級、PP、恢復吸取、先制等大量句子多半是句型變體，**加解析規則就好，不要新增 op**。每加一條規則，都要跑 `audit:block-migration` 看解鎖了幾句。

### P5 移除舊路徑

## 5. 風險

| 風險 | 對策 |
|---|---|
| 舊存檔的自訂精靈或 kit 壞掉 | P1 自動轉換，保留 `legacyKit`，並寫往返測試 |
| handler 和 kit 同時執行，效果結算兩次 | 切換與刪除 handler 分支在同一個 commit；加入「同一定義只走一條路」的斷言 |
| 原文改了但定義沒跟上 | 已有 `sourceSha256`；過期定義在戰鬥中顯示「效果待接通」，不執行舊定義 |
| 解析規則過寬，吞掉半句 | 規則一律錨定整句；每條規則都附反例測試 |
| 驗證成本高 | 連鎖驗證已有快取；P5 改讀快取的 Clause 之後，戰鬥中不再解析 |
