# 賽爾號立繪動畫機制解析

> 建立：2026-11-04
> 資料來源：`public/elf-anim/wuxu_liuren/manifest.json`（正常版，19 KB）
> 目的：解釋「為什麼官方立繪能動又不突兀」，以及骨骼方案為何失敗

---

## 一、核心答案

**官方不是「讓立繪動起來」，而是「播放畫師畫好的連續圖」。**

- 每幀都是一張完整的手繪圖（序列幀）
- 播放時只換「UV 採樣區」，頂點位置幾乎不動
- 頂點只做 ±1% 的微調（呼吸感）

**骨骼變形從頭到尾都不存在。**

---

## 二、資料結構（每幀 21 個數）

```json
{
  "c":   [0.6,5.28, 3.98,5.28, 3.98,0.31, 0.6,0.31],
  "a":   1,
  "f":   [2.45,3.58, 3.66,3.58, 3.66,2.37, 2.45,2.37],
  "fuv": [0.0849, 0, 0.1153, 0.0809]
}
```

| 欄位 | 長度 | 含義 | 是否變化 |
|---|---|---|---|
| `c` | 8 | 原始框（4 個角的基準位置） | 固定 |
| `a` | 1 | 透明度 | 通常 1 |
| `f` | 8 | 當前 4 角位置 | **幾乎不變**（±0.02 單位） |
| `fuv` | 4 | UV 採樣區（u0,v0,u1,v1） | **每幀變化** |

**8 個數 = 4 個頂點 × (x,y)。這是一個矩形，不是網格。**

## 三、動畫怎麼動

### 主要機制：UV 橫向平移

```
幀0: u0=0.0849 → u1=0.1153   寬度 0.0304
幀1: u0=0.1153 → u1=0.1457   寬度 0.0304
幀2: u0=0.1457 → u1=0.1761   寬度 0.0304
幀3: u0=0.1761 → u1=0.2065   寬度 0.0304
幀4: u0=0.2065 → u1=0.2369   寬度 0.0304
```

**每幀 UV 平移 0.0304 = 1/32（atlas 寬度 ÷ 幀數）。**

**atlas.png 橫向排列 32 張圖，每幀取一張。**

### 輔助機制：頂點微縮放

```
幀0-4: f = [2.45,3.58, 3.66,3.58, 3.66,2.37, 2.45,2.37]
幀5-7: f = [2.44,3.59, 3.67,3.59, 3.67,2.36, 2.44,2.36]
       ↑ 每邊擴 0.01（約 1%）
```

**32 幀中有 19 幀有這種微調。**

**作用：呼吸感，避免「靜止的圖片」。**

### 不突兀的三個設計

| 設計 | 作用 |
|---|---|
| **序列幀（UV 平移）** | 每幀都是畫師手繪的完整圖，天然連貫 |
| **頂點微縮放（±1%）** | 呼吸感 |
| **24 FPS** | 與影視標準一致 |

## 五、骨骼方案為什麼失敗

### 根本誤判

| 項目 | 官方做法 | 骨骼方案 |
|---|---|---|
| 動畫來源 | 畫師手繪序列幀 | 程式變形 |
| 頂點數量 | **4 個**（一個矩形） | **2,976 個**（48×62 網格） |
| 每幀存什麼 | **UV 座標** | **全部頂點座標** |
| 變形方式 | 無（換圖） | 蒙皮計算 |

### 資料爆炸的數學

```
48 × 62 網格 = 2,867 個四邊形/幀
每個四邊形 16 個浮點（8 位置 + 8 UV）
每幀 = 45,872 個數
182 幀 = 834 萬個數
按 JSON 序列化 ≈ 41.9 MB
```

### 效能影響

| 項目 | 數值 |
|---|---|
| 每幀繪製 | 2,867 個 quad |
| 24 FPS | 68,808 次/秒 |
| 正常動畫 | 1 個 quad/幀 |
| **倍數** | **2,867×** |
| 單隻記憶體 | 約 126 MB（JSON 解析膨脹） |
| 6v6 隊伍 | 約 1.5 GB |

## 六、正確的做法

### 若要「自製動畫」

**必須先有序列幀素材（每幀一張圖），然後：**

1. **把幀拼成 atlas**（橫向排列）
2. **每幀只記 UV 區間**（4 個數）
3. **頂點用固定矩形**（8 個數，可選微調）
4. **輸出 manifest**（約 19 KB）

**不需要骨骼、不需要網格、不需要蒙皮。**

### 若要「從單張立繪生成動畫」

**這才是難點。可能的做法：**

| 方法 | 可行性 | 說明 |
|---|---|---|
| **A. 局部圖層位移** | ✅ 推薦 | 把角色拆成頭/身/手/武器，各自微幅位移 |
| **B. 頂點微變形** | ✅ 可行 | 用少量頂點（20-50 個）做呼吸/擺動 |
| **C. AI 生成序列幀** | ⚠️ 成本高 | 用 AI 生成 16-32 張連續幀 |
| **D. 骨骼蒙皮** | ❌ 不推薦 | 資料量爆炸，且 2D 位圖沒有骨骼資訊 |

**你的 Lively 壁紙走的是 A 路線（分層 + Spine 骨骼），但那適用於桌布（4K、單一角色、無需 6v6 同屏）。**

**遊戲內需要 12 隻精靈同屏，必須控制在 KB 級。**

## 七、結論

### 官方動畫的本質

```
一張 atlas（32 幀橫排）
+ 每幀 21 個數（UV + 頂點 + alpha）
= 0.76 MB，24 FPS 流暢播放
```

### 關鍵洞察

1. **「動」來自畫師畫的 32 張圖，不是程式變形**
2. **程式只負責「按時間換圖」**
3. **頂點微調（±1%）負責「不僵硬」**
4. **資料量極小是因為只存 UV，不存頂點**

### 對自製動畫的建議

**如果素材是「序列幀」→ 照官方格式打包（19 KB）**
**如果素材是「單張立繪」→ 用局部圖層位移（方法 A），不要用骨骼蒙皮**
