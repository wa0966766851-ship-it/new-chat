# 積木系統重建：操作與內部合約

## 本輪範圍與完成界線

這輪已改動資料合約、儲存／匯入、本地解析、正式戰鬥路由及 UI，不是只換畫布外觀。沒有把所有既有精靈直接改成手動 Kit 執行，也沒有宣稱所有效果逐句正確。

- 所有 42 隻預設精靈的魂印、特質、攜帶／預備技能都有結構檢視與來源核對入口。原文不自動覆寫。
- 入口測試枚舉 483 筆（含攜帶／預備重複）；遷移清單按同隻技能名稱＋描述去重後共 369 份定義。
- 嚴格轉換器：27 份完整候選、342 份仍需補條件／原子／時點。候選不是語意通過；沒有自動切換任何預設卡牌。
- 原逐句稽核仍為 1880 個效果子句：1867 待核對、13 份舊證據因依賴變更過期，完整逐句驗收數為 0。這不代表程式沒有任何效果，而是不能把局部測試換算為全卡正確率。

完整清單：[積木遷移](audits/block-migration.md)、[候選Kit與阻擋原因JSON](audits/block-migration.json)、[逐句實裝稽核](全精靈效果實裝核對.md)。

## 操作流程

`原文核對 → 節點畫布 → 驗收清單 → 儲存精靈`

1. 原文核對：選魂印、技能或任一特質，確認單一執行來源。只有整份原文能等價轉換時才開放「煉成可編輯積木」；複雜／未知句保留，不換成近似模板。
2. 節點畫布：先選戰鬥階段，再選正式時點，放入條件、目標、行為、固有／附加／攜帶與傷害範圍。進入此頁才載入Blockly核心，既有公開序列化格式保留。
3. 驗收清單：保留原描述，逐句／詞條列出觸發、條件、行為／目標、完整參數與未解析片段，可匯出JSON核對資料。沒有自動通過標記。
4. 畫布即時同步的是草稿，不是正式存檔。關閉即時同步後需按「套用畫布到草稿」；同工作區切頁仍保留畫布，未套用時不能切換效果對象。離開整個精靈編輯頁仍需先套用、儲存。

## 內部來源與真實節點

新增 `src/effects/effectNodes.ts` 統一 27 個節點的中文名稱、戰鬥階段、正式事件、衍生入口及說明。編輯器、Kit顯示模型、生命週期路由共用，不再各自手寫一份名稱表。

- 戰鬥開始：首發登場衍生入口，不偽造不存在的枚舉。
- 主動切換前、下場、致命抵擋、死亡節點一分開，不把死亡等同於0血。
- 受到傷害後採 `ON_DAMAGED`，不重播同義 `AFTER_DAMAGE`。
- 失敗收尾採 `ACTION_FAILED`，已接通手動魂印／特質與其他攜帶槽；本次技能 `on_invalid` 由技能runner處理一次，不與雙側 `SKILL_INVALID` 重播。
- 使用技能及常駐傷害修正是直接／衍生入口，不把所有枚舉一律當成可執行節點。
- 額外行動開始／結束與連擊分開，動畫數量不決定邏輯節點數量。

`effectMode` 支援 auto／description／kit／registry。手動來源不再同時執行舊描述、同名技能handler與模板；缺註冊表或尚未實裝原子明示待接通。■固有、🎯附加、◇攜帶分流，技能封附加不誤封固有。未使用槽只有攜帶效果可以監控其他技能。

幻化取得效果只借用魂印與特質定義，不借用對手側、戰鬥身分或整套技能。精靈名稱的舊特質補登不能覆蓋明確手動來源；未修改特質保持原來源。

## 效能處理與驗收

- 原文／驗收頁不建立Blockly畫布；首度開啟畫布後，內部切頁保留同一工作區，避免重複載入及丟失未同步內容。
- 拖曳採250ms防抖，初始載入停用事件，不能只因打開畫布就把來源改成Kit。
- 原子驗證使用512項上限的內容快取；舊程式原地修改參數也會重新校驗，過長資料不納入快取。原子不合法仍拒絕執行，不用效能理由取消校驗。
- 尚未取得實體低階手機FPS、長任務或記憶體數據；沒有「保證不卡」的結論。

自動驗收：正式Vite註冊表、Blockly公開存檔／重載、React畫面煉成、編輯儲存／圖紙重載、P1／P2及附加失效真實戰鬥；不只是對戰不崩潰。瀏覽器驗收包含三分區、按需載入、七階段選單、手動同步關閉後切頁保留及套用後核對。未將測試草稿儲存到使用者卡牌。

驗收中重現控制中心載入舊版動態檔案後整頁空白；現已在面板外加局部錯誤邊界，提供關閉／確認後重新載入，不自動清除存檔或刷新。更新後的舊分頁仍可能需要使用者重新載入，但失敗不再連帶卸載主頁。

- `npm run lint`、完整 `npm test`、`npm run build` 均以退出碼0完成；新增連接測試為21個語意檢查＋10個整合情境，頁面恢復測試7項通過。

- 瀏覽器實際確認預設原文核對、畫布按需載入與七階段分類；草稿未儲存為使用者卡牌。截圖：`build/block-workflow-nodes-20261009.jpg`、`build/block-workflow-verification-20261009.jpg`。

5. 以正式效能觀測資料決定分頁／批次／Worker；最後再逐頁與低階裝置驗收。編輯器整體離頁的未套用畫布提示也需強化。
