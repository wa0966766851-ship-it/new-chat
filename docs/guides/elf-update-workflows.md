# 精靈更新：積木與 AI 協作

側邊欄「更新與精靈」整合更新公告、新精靈介紹、精靈更新指南。公告描述目前載入版本，不是伺服器已更新的保證；版本檢查仍在控制中心。

## 途徑一：透過積木整合

1. 在精靈更新指南選擇目前使用的精靈，先「匯出目前圖紙」備份。
2. 按「用積木編輯」，進入既有精靈編輯器的積木頁。
3. 同步修改技能、魂印或特質原文與積木。逐條核對觸發、條件、目標、行為、期限；命中後取得持續效果，與持續期間使用技能觸發，是不同時點。
4. 檢查積木支援狀態。缺少動作或事件時保留原文，交維護者補通用機制，不用空動作、近似傷害或專屬包裝充數。
5. 確認後儲存至本機，於實戰演練測雙方、持續期限、換人與傷害數值；也可使用編輯器既有驗證工作台。格式通過與實戰結果分別記錄。
6. 匯出完成圖紙，供其他玩家匯入或交維護者整合。

## 途徑二：交由 AI 協助

1. 選擇同一份精靈資料，填寫原文、修改需求與預期結果。
2. 複製 AI 更新任務，或下載文字檔，貼給使用者自行選擇的 AI。此操作不呼叫外部 AI、不消耗應用 AI 額度，也不讀取帳戶金鑰或其他存檔。
3. 任務附帶既有 schemaVersion 2 圖紙。現有積木足以表達時，AI 回傳完整 JSON；缺機制時，由能存取專案的 AI 補共用合約、事件入口、實際讀取端與測試。僅能聊天的 AI 應列出缺口，不宣稱已改程式。
4. 將 JSON 存為檔案，按「匯入圖紙」。先看名稱、技能數與警告，確認後才送往積木編輯器；尚未自動儲存。
5. 按與積木途徑相同的方式核對、測試與儲存。不執行 AI 回覆中的任意程式碼。

兩條途徑共用 `parseElfBlueprint`、編輯器、Kit 合約與本機保存，沒有另一套 AI 專用戰鬥實作。匯出目前資料不會修改來源；匯入仍沿用既有 2 MB 限制及結構校驗。

未完成的原稿也可以匯出備份或交給 AI 修復，不會因原稿尚未通過積木校驗而失去備份機會。這不會放寬回傳圖紙的匯入校驗；AI 仍須修正非法積木，才能匯回編輯器。

## 公開給所有玩家

本機桌面完成版本使用 `npm run desktop:update`；這與網站／EXE發布分開。固定捷徑、驗證後切換、前一版本回復、存檔保留與皮膚朝向規則見 [桌面完成版本指南](desktop-completed-version.md)。

本機儲存與圖紙分享不會寫入 GitHub 或其他玩家的倉庫。維護者需：

1. 核對真實 repo、AGENTS.md、最新接續紀錄及工作樹，保留其他修改。
2. 把精靈定義與可編輯 Kit 整合至正式資料載入途徑；新機制須有查詢／事件讀取端，不往 BattleScreen 或 battleEngine 加精靈專屬分支。
3. 按範圍跑 P1/P2 正式引擎行為／數值、保存重載、型別檢查與建置。Kit 變更執行 `npm run data:kit-pack`，新增素材核對來源與朝向。
4. 更新 `src/data/releaseNotes.ts`：公告寫已收錄的變更，精靈介紹登記正式 ID，詳細魂印／技能直接使用目前資料，不另複製一份技能定義。
5. 網站沿既有 `Build website package without AI` 工作流發布，須通過完整測試再啟用；新 EXE 另行遞增版本並封裝發布。玩家再由控制中心載入新版。

目前全套發布仍受斯嘉麗回歸等既有問題阻擋，不能因本頁與更新測試通過而視為全專案驗收。詳見 `docs/audits/網站發布前複檢_20261020.md` 與 `docs/audits/內建更新實測_20261020.md`。

## 本功能驗證

`npm run test:updates-page` 實際載入新頁面、介紹詳細資料、積木入口、AI 任務、檔案匯入預覽與確認，驗證 Kit 保存及本機存檔不被提前修改。`npm run test:updates` 包含本測試與原更新功能回歸；另執行 lint、build 及 bundle 預算檢查。

2026-10-20 本輪驗證通過：新頁面互動與圖紙流程、剪貼簿失敗時下載替代提示、介紹頁 Escape／焦點恢復、原編輯流程 7 場景、更新相關回歸、型別與正式建置。首頁初始 JS 706.38 kB，95 個頁面／Worker 塊均低於 500 kB；新頁面為延後載入。未開真實瀏覽器或 Windows EXE 前台驗收；這些結果不解除既有全套戰鬥回歸的發布阻擋。


## 共用介紹模板與入口

介紹由 `src/components/ElfSpotlight.tsx` 和樣式檔統一呈現，直接讀取 Elf 的立繪、魂印、特性、技能及種族資料，沒有另外複製技能文案。更新入口每次一隻，可搜尋替換，僅記住精靈 ID；資料更新會同步顯示。傳入 `selectedElf` 可鎖定指定個體並使用「精靈介紹」標題，隱藏替換按鈕。百科／戰鬥的既有 `ElfReadOnlyProfile` 提供「完整介紹」入口，隱匿對手不提供入口。關閉後返回原面板，並不改寫更新入口的展示選擇。

技能沿用現有屬性圖標，物理／特殊／屬性技能及威力、PP、充能各有圖標與文字提示。桌面優先完整三欄，小螢幕允許捲動以保留完整原文；較長的自訂精靈仍須逐隻驗收。

## AI 檢查同類接線問題

更新指南的「複製 AI 任務」已附檢查要求。維護者先執行 `npm run audit:elf-wiring -- --id=5021`，全池使用 `npm run audit:elf-wiring -- --out=docs/audits/elf-wiring-20261023.json`。報告會包含技能池，檢查來源定義、模式、正式路由與 Kit 節點；零結構錯誤不代表語義正確。

交接給 AI 時要求逐條提供：

1. 原文 → 觸發／條件／目標／行為／數量／期限，歧義明列。
2. 正式資料來源 → effectRoute → 發出事件 → operation → 狀態讀取與消費 → 清除時點的實際檔案位置。
3. P1／P2 正式引擎數值測試，涵蓋死亡、板凳、回場、重複初始化及下回合期限。必須有觸發與不觸發反例，不能只測 handler 或不崩潰。
4. 傷害分別核對公式、追加、克制、增減傷、保底、護盾、實際扣血；防止誤用真傷或粉傷。
5. 匯出／重載後完整參數一致，修改 Kit 後正式戰鬥確實改變，舊 handler 不得蓋過 Kit。舊存檔、自訂資料與畫面播放另列證據，沒有測就標未驗證。
6. 專屬行為不得加入 BattleScreen／battleEngine；補通用積木合約與消費端，再跑相關回歸、型別與建置。

本輪全池結構檢查：43 隻、含技能池 397 條定義、0 結構問題；這不是全池行為完成聲明。次元龍可用 `npm run test:dimensional-complete` 重跑 20 組修正、先制及 14 組魂印生命週期測試。

九青接手修正可用 `npm run test:jiuqing` 重跑。檢查前先核對 `docs/audits/jiuqing-fixes-20261023.md` 的逐條觸發／目標／期限與使用者確認的語意；不得以成功打包取代行為數值證據。舊存檔更新也須測「精確匹配舊內建才更新、自訂保留、PP／配裝保留」。
